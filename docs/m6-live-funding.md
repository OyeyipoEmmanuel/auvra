# M6 Bachs funding and procurement controls

The Bachs USD rail is opt-in. Set `BACHS_USD_ENABLED=true`, `BACHS_API_KEY`, and `BACHS_WEBHOOK_SECRET` server-side. `AUVRA_RUNTIME_MODE=DEMO_SANDBOX` accepts only `sk_sandbox_` and labels resulting payments `BACHS_SANDBOX`; `LIVE_MARKET` accepts only `sk_live_` and labels them `BACHS`. Without a configured rail, demo quotes remain USDC and can use the existing simulated funding path. Existing Paystack records remain historical; no new Paystack checkout or webhook is offered.

When Bachs is configured, discovery prices supplier listings in USD and only accepted, same-asset, two-decimal USD quotes can enter checkout. Auvra creates a [raw-price checkout session](https://docs.bachs.io/guides/checkout/checkout-sessions) in the matching Bachs environment, restricted to USD card. When `AUTH_URL` is public HTTPS, the session includes an Auvra `success_url` and `cancel_url`. The success page matches Bachs' appended `checkout_id` to the authenticated customer's stored checkout. A pending payment can be reconciled against Bachs' checkout and charge APIs from the request page or return page. The same idempotent allocation path handles both direct verification and signed webhooks. The browser redirect alone never funds a project. Localhost success redirects are not sent because Bachs rejects private URLs even in sandbox; return to the request manually and use **Check payment status**. Do not start another checkout or delete a successful payment.

For local signed-webhook testing, expose the local app through a temporary public HTTPS forwarding URL (for example, `ngrok http 3000`). Set the Bachs sandbox endpoint to `https://<your-forwarding-domain>/api/payments/bachs/webhook`, subscribe to the collection and risk events below, and use the endpoint's matching `BACHS_WEBHOOK_SECRET` in the local server environment. Restart the local server after changing the secret. Direct reconciliation is a fallback for a delayed/missed collection webhook, not a substitute for testing signed webhook delivery and risk events before live use.

The Bachs webhook is `POST /api/payments/bachs/webhook`. Subscribe to `collection.succeeded`, `refund.created`, `refund.paid`, `dispute.created`, and `dispute.updated`. The route verifies the [V2 HMAC-SHA256 signature](https://docs.bachs.io/guides/webhooks/overview) on raw bytes and rejects stale timestamps. A real `collection.succeeded` must have a charge ID; test events with a null charge ID do not allocate. Auvra retrieves the payment through the Bachs API and matches reference, checkout ID, charge ID, amount, amount paid, USD asset, and success status. Unique provider event IDs make delivery idempotent. Signed risk notices hold the project. Refund cash movement and provider fee/settlement reconciliation still require separate evidence and journals.

`BACHS_SANDBOX` receipts are simulated, visibly labelled, journaled in `DEMO_USD` rather than the live USD ledger, and cannot pass the live spend or public receipt-anchor gates. Even `BACHS` live customer payment does not prove a funded NEAR Agent Market buyer account. The worker requires an authoritative recent marketplace balance/method probe, exact asset, policy caps, and approval before a hire; this probe remains unconnected, so hiring fails closed. No USD-to-USDC conversion or 1:1 live assumption is made.

The local payment tests mock provider responses. Before live enablement, verify Bachs merchant USD-card eligibility, fees, refunds/disputes, settlement, and an actual signed webhook roundtrip in the merchant account. Keep API and webhook secrets off the client and out of version control. The Rust receipt registry is hash-only evidence, not a payment or escrow contract.
